# 确定自动与手动重命名的并发协调

## Question

定时重命名器、用户立即应用和失败重试同时发现同一命名单元时，如何只让一个执行者推进当前已确认修订，并阻止过期修订在用户再次编辑后继续改名？

## Resolution

所有入口统一提交到同一套按命名单元串行化的执行器：

- 用户点击应用时，先在事务内持久化单调递增的已确认修订并标记旧修订被取代；接口随后触发执行器，但不直接调用下载器改名。
- 定时器、立即触发和失败重试都必须通过数据库条件更新领取同一命名单元的有界租约，并携带修订号和单调递增的栅栏令牌；没有租约不得改变文件。
- 每次调用下载器前以及每个状态推进点都重新验证租约、栅栏令牌和当前已确认修订。租约过期的旧执行者即使稍后恢复，也不能提交状态或继续下一步。
- 若新修订获批时旧执行尚未改变文件，旧执行立即退出；若命名单元已进入部分改名，则旧执行只完成恢复到一致状态所需的前向步骤，然后释放租约，由新修订基于实际文件状态继续。
- 一个外部下载器调用无法撤销或中断；调用返回后若发现修订已过期，只记录实际结果，不再执行剩余旧目标。
- 重试始终复用同一已确认修订和幂等操作记录；目标路径唯一预留，用户只看到最新修订的状态，旧修订保留审计历史。
